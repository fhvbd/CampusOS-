# 一、为什么要做这份验证

02_PRD需求文档 与 05_系统详细架构设计书 中提到的"通知聚合""课表同步"，目前只有目标描述（来源：教务系统/学工处/学院通知），**没有说明具体如何取得数据**。这是当前整个项目最大的不确定项：

- 如果拿不到教务系统数据，V0.2 通知中心、V0.3 课表中心两个核心 MVP 模块就无法落地，需要重新设计产品形态。
- 如果需要托管学生账号密码去爬取数据，会引入远超"功能范围"的安全与合规责任，必须提前想清楚，而不是编码过程中才发现。

**原则**：本验证必须在 V0.1 编码正式开始前完成，作为 V0.2/V0.3 是否能按原计划推进的前置条件。

# 三、每类数据源需要确认的问题

对上表中每一行，逐一回答以下问题，形成结论：

1. **是否存在官方开放接口**（教务系统 API、微信服务号接口等）？
2. **如果没有官方接口**，是否可以通过网页端模拟登录 + 页面解析获取数据？
   - 登录是否需要验证码 / 短信验证 / 图形验证码？
   - 登录态（session/cookie/token）的有效期多长？
   - 页面结构是否稳定，是否为服务端渲染（便于解析）还是纯前端渲染（需要额外处理）？
3. **数据更新频率**：课表/通知多久会变化一次？决定同步策略（10_数据流设计书中的"数据同步策略"需要据此调整）。
4. **是否需要保存学生的教务账号密码**？如果需要，保存在哪里、如何加密（直接关联 15_隐私安全设计.md）。
5. **是否有使用条款/服务协议明确禁止第三方爬取**？如果有，需要评估合规风险，或改为"用户手动导入/截图识别"等替代方案。
6. **失败/异常场景**：教务系统改版、临时不可用时，App 如何降级（参考 10_数据流设计书"异常处理"）。

# 四、验证方法（Spike 建议）

不需要写产品代码，只需要一个可丢弃的脚本验证结论：

1. 用自己的账号，手动登录一次教务系统，观察登录请求、返回的 Cookie/Token。
2. 写一个最小化脚本（Python requests / Playwright 均可），复现登录流程，抓取一次课表页面。
3. 抓到页面后，判断能否稳定解析出课程名称/教师/教室/时间等结构化字段。
4. 通知公告页面同样跑一次，确认列表和详情的字段是否可解析。
5. 记录以上过程中遇到的验证码、加密参数、接口限流等障碍，形成结论。

# 六、根据结论的后续路径

- **完全可行**：按原计划推进 V0.2/V0.3，crawler 目录按计划实现自动同步。
- **部分可行**（如通知可以但课表拿不到）：调整 MVP 范围，暂时改为"用户手动录入/导入课表"，保留自动同步为后续迭代目标。
- **完全不可行**：需要与产品目标重新对齐——是否改为"用户手动维护课表 + Excel/图片导入"的轻量方案，重新评估通知中心/课表中心的实现方式，并同步更新 02_PRD需求文档、04_开发路线图、12_开发任务拆解(WBS).md 中的相关任务。

---

# 七、与安全设计的关联

如果验证结论中出现"需要保存学生账号密码"的情况，必须在启用前完成 15_隐私安全设计.md 中"第三方凭证托管"相关章节的设计（加密方式、存储位置、是否允许用户随时解绑），不得先实现功能后补安全措施。
