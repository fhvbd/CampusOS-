# CampusOS 隐私与数据安全设计

版本：V1.0
关联文档：05_系统详细架构设计书.md（第十章·安全设计）/ 06_数据库设计书.md / 14_数据源可行性验证.md

---

# 一、为什么需要这份文档

05_系统详细架构设计书 第十章"安全设计"目前只有五个词条（密码加密存储、Token认证、接口权限验证、日志审计、异常处理），没有展开说明具体做法，也没有覆盖"数据"本身的隐私问题（存什么、存多久、谁能看到、出问题怎么办）。

CampusOS 存储的信息包括学号、课表、通知、待办事项，未来可能还包括教务系统账号密码（见 14_数据源可行性验证.md）——这些都属于需要认真对待的个人信息，本文档在原有安全设计基础上做具体补充。

---

# 二、数据分类与敏感级别

| 数据 | 对应表（06_数据库设计书） | 敏感级别 | 说明 |
| --- | --- | --- | --- |
| 登录密码 | users.password_hash | 高 | 必须哈希存储，禁止明文 |
| 学号 | users.student_id | 中 | 可识别个人身份 |
| 课表 | courses | 低 | 结合学号可反推个人日程 |
| 待办事项 | tasks | 低～中 | 内容可能涉及个人隐私（如"看病"） |
| 通知 | notices | 低 | 公开信息，风险小 |
| AI 对话记录 | ai_records（V0.5起） | 中～高 | 可能包含用户主动透露的个人信息 |
| 教务系统账号密码（如需托管，见第五章） | 待新增表 | 极高 | 一旦泄露影响用户校内其他系统 |

---

# 三、密码与身份认证

1. **密码存储**：使用 bcrypt/argon2 等加盐哈希算法，禁止自实现哈希或使用不加盐的 MD5/SHA1。
2. **Token 认证**：JWT Token 设置合理过期时间（如 7 天），过期后要求重新登录；支持服务端主动使 Token 失效（如修改密码后）。
3. **接口权限验证**：所有涉及用户数据的接口必须校验 Token 归属，禁止 A 用户通过接口访问 B 用户数据（尤其是 `/api/task/*`、`/api/notice/read/{id}` 等按 id 操作的接口，需校验数据归属而不仅是登录状态）。

---

# 四、数据存储与传输

1. **传输加密**：全部接口走 HTTPS（对应 07_API接口设计书"协议：HTTPS"），开发阶段本地测试可临时使用 HTTP，但上线前必须切换。
2. **数据库层面**：
   - 开发阶段 SQLite 文件本身不加密，仅限本地开发使用，不得随意上传/分享数据库文件。
   - 迁移到 PostgreSQL（生产阶段）后，建议对 `password_hash` 之外的敏感字段视情况加密存储，数据库访问账号权限最小化。
3. **本地缓存**（对应 10_数据流设计书"数据缓存"）：课表、通知、用户信息等本地缓存数据，退出登录时应清除，避免共享设备残留他人信息。

---

# 五、第三方凭证托管（视 14_数据源可行性验证 结论决定是否需要）

如果验证结论显示"需要保存学生的教务系统账号密码"才能实现自动同步课表/通知，必须遵守以下原则，而不是直接明文存库：

1. **能不存就不存**：优先考虑"用户在客户端本地登录教务系统、由客户端完成抓取后仅上传结构化结果"的方案，避免密码经过服务端。
2. **必须存储时**：
   - 使用对称加密（如 AES-256）加密后存储，密钥由服务端环境变量管理，不入库、不进代码仓库。
   - 提供用户主动"解绑/删除"入口，解绑后立即删除该密文。
   - 明确告知用户该密码的用途和风险，获得用户明确同意（而非默认勾选）。
3. **禁止行为**：禁止将教务系统密码明文写入日志、禁止在崩溃报告/埋点中带出密码相关字段。

# 六、日志与审计

1. 日志中禁止记录：密码明文、Token 完整内容、教务系统账号密码。
2. 异常日志（对应 05_系统详细架构设计书"日志审计"）应记录：接口路径、时间、用户 id（非敏感标识）、错误类型，用于排查问题，而非用户行为画像。
3. 日志保留期限建议设定上限（如 90 天），超期自动清理，避免无限期积累。

---

# 七、用户数据权利

MVP 阶段建议至少支持：

1. **账号注销/数据删除**：用户可以要求删除账号及关联的课表、通知已读状态、待办事项等数据。
2. **数据导出**（可选，非 MVP 必须）：用户可导出自己的待办/课表数据。
3. **隐私说明**：在登录/注册页提供简要说明，告知采集了哪些数据、用途是什么，不需要长篇法律文本，但要真实准确。

---

# 八、AI 模块相关的额外注意事项（V0.5 起）

1. 用户上传给 AI 的 PDF、提问内容，如果会调用外部模型（OpenAI/Claude/DeepSeek），需要在产品内明确告知"内容会发送给第三方AI服务商处理"。
2. `ai_records` 表存储的对话记录，敏感级别较高，建议：
   - 提供用户删除单条/全部 AI 记录的功能。
   - 不用于除"提供服务"之外的其他用途（如不用于模型训练、不对外分享）。

---

# 九、与项目铁律的关系

安全与隐私设计不是"锦上添花"的功能，而是"高频且不可逆风险"的防线，其优先级应高于任何锦上添花的产品功能。建议：

- 涉及用户数据的接口，在 12_开发任务拆解(WBS).md 每个任务验收时，都增加一条"是否符合本文档要求"的检查项。
- 若 14_数据源可行性验证 结论要求托管第三方账号密码，则第五章的方案设计必须在对应功能编码前完成评审，不得先实现后补。
